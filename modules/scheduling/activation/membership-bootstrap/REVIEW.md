## Checksums and immutability

`artifactChecksums()` calculates SHA-256 for the five files in `ARTIFACT_FILES`. The bundle checksum is SHA-256 of the UTF-8 concatenation of sorted entries `file_sha256`, two spaces, filename, newline. `SHA256SUMS.json` records those results. `VALIDATION.json` is evidence, not part of the signed bundle, avoiding a circular checksum. Owner approval must independently bind the bundle checksum, and execution recomputes it both during authorization and before transaction entry. Git and the external approval record retain the reviewed version. Any edit requires a new digest and approval; file permissions or a mutable manifest alone do not establish immutability.

## Parameterized transaction and abort conditions

`executeGrant` is the exact administrative procedure. Values in queries are bound through pg parameters, not interpolated. Its fixed transaction sequence is:

1. SERIALIZABLE; local lock timeout 5s, statement timeout 30s, idle-transaction timeout 30s, UTC timezone.
2. Server database/session/current-principal validation; disposable mode additionally requires a local-only server marker.
3. SHARE table lock on Auth user and SHARE ROW EXCLUSIVE table locks on members and both audit tables, then FOR UPDATE lock on the exact tenant. These brief table-wide locks deliberately protect absent keys, identity stability and audit-trigger definitions. Abort on contention; no retry loop. Mutation relations must be plain tables without RLS, custom rules or unreviewed user triggers. Known trigger names/types/bodies/enabled state are checked; non-origin replication modes and cascading membership dependencies are rejected. Local search_path is pg_catalog.
4. Exact tenant UUID/slug and disabled-state check. Exact existing Auth UUID must be verified and not banned. Reject consumed operation IDs and any existing membership.
5. One INSERT into members, relying on defaults for timestamps, no upsert or conflict recovery.
6. One tenant_audit INSERT and one platform_audit INSERT, then COMMIT. Any validation or pre-commit query error rolls back. Errors during COMMIT are classified conservatively as ambiguous, including errors that may have actually aborted.

The membership unique key, check constraints, tenant foreign keys, timestamp update trigger and immutable platform audit trigger are represented from previously captured schema metadata (`user_read_only_context/tool_content/inspecting-approved-staging-schema-neon-run-sql-7-ln-h.txt` and `user_read_only_context/tool_content/inspecting-membership-constraints-and-triggers-neon-run-sql-nlr-l.txt`) and repository migrations 001, 007, 009. Reading those saved files is offline evidence review, not a fresh Neon schema inspection. The fixture is not a full Auth or Scheduling schema clone. Unrelated tables are minimal synthetic sentinels. Before future execution, separately approved live read-only schema/trigger/privilege inspection is mandatory, including assurance that no new insert/delete triggers produce unreviewed side effects. No schema is modified by the execution procedure.

Audit action is `staging_membership_bootstrap`; actor is the actual external operator subject. Metadata includes operation/approval/evidence references, owner/operator/attestor, authorization-document digest, artifact digest, target, environment, database/session principals, endpoint, tenant audit ID, before=null and exact inserted row. Failed transactions retain no database audit, so retain external execution evidence and receipts. Existing privileged database users can defeat database audit protections; external evidence is essential.

## Ambiguous commit and read-only verification

No automatic retries exist. If COMMIT acknowledgment fails, `AmbiguousCommitError` contains the operation ID and the dedicated connection is closed. Even a known test transport failure must not cause a second grant attempt. Retain the exact signed envelope and receipt context.

Using a newly connected independently target-verified Client, `readOutcome(client,token)` executes a REPEATABLE READ READ ONLY transaction. It checks exact membership, successful operation audit, authorization/artifact digest, matching tenant audit and operator. It returns COMMITTED, NOT_OBSERVED_NO_AUTOMATIC_RETRY, or MANUAL_REVIEW. NOT_OBSERVED is not permission to retry; lag, ongoing commit, or inconsistent evidence require operator reconciliation. An expired authorization needs a separately reverified read-only review process; do not re-sign it to replay the grant. The read function never mutates data.

Before and after any eventual approved execution, independently capture aggregate hashes/counts of non-target memberships, platform administrators, tenant enabled state/configuration, hosts, billing, notifications, booking settings, appointments and availability. Compare unchanged state and require exactly one new target membership and two matching audit rows. Do not log customer rows or credentials.

## Separate rollback procedure

`executeRollback` requires a newly signed `action=rollback` document, new operation ID and separate approval reference, original platform audit UUID in `rollbackOf`, and `restorePreGrantNoAdminState=true`. Both signers must approve restoring the original state, including removal of the last tenant administrator if applicable. No original audit is deleted or updated.

`activityEvidence` must include `complete=true`, `noInterveningActivity=true`, independent evidence `reference`, `quiescenceReference`, and millisecond `coverageFrom`/`coverageThrough`. Coverage must start no later than the original grant and extend through authorization issuance; independently verified quiescence must remain in effect through transaction completion. This is an attested external fact, NOT inferred from timestamps. If exhaustive activity evidence or quiescence is unavailable, stop for manual review; the existing schema alone cannot prove absence of legitimate use.

The rollback rechecks all target/identity/disabled-state guards, locks as above, verifies the original successful grant scope/digest and separate approval, and deletes exactly the membership matching the entire original JSONB row including timestamps. Changed/missing membership or a foreign-key dependency aborts. Exactly two new rollback audits are appended atomically, referencing the original grant. Removing other data, cascading deletes, reverting third-party legitimate changes, or silently bypassing administrator protection is prohibited.

## Disposable test harness

`bootstrap.unit.test.mjs` exercises signature/target/digest/expiry/environment gates without any database connections. `bootstrap.pg.test.mjs` launches a brand-new local PostgreSQL cluster with Unix sockets only, TCP disabled, a scrubbed child environment, database neondb and a synthetic-only server marker. It accepts an explicit binary-directory argument; it never reads DATABASE_URL, PG*, provider credentials or project env files. It never imports application code or prior Neon runners. All account fields are synthetic; the pinned UUIDs serve only as reference identifiers. All test signing keys/subjects/approvals are generated TEST_ONLY fixtures, not actual approval evidence. The runner stops its own server and removes its exact mkdtemp directory on completion.

No live connection creator/CLI is supplied. The PostgreSQL suite covers SQL/constraints/triggers, competing sessions, timeouts, duplicate/conflicting memberships, both audit-insertion failures, atomic write scope, rollback safeguards, and both acknowledged-server-commit/lost-client-ack and uncommitted lost-ack outcomes. Unit success is not PostgreSQL success. See VALIDATION.json for checks actually run and environment blockers.
